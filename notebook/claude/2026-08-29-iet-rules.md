## Maths I checked rather than transcribed

**Wedge test.** Sound. If $J$ lies in a closed convex cone of opening $\theta < 60°$ with apex $O$,
then for $P,Q \in J$ we get $\angle POQ \le \theta < 60°$, and an equilateral triangle needs exactly
$60°$ at each vertex, so $O$ is not a vertex. The 30-30-120 triangle works as a witness because it
is **convex**: at a $30°$ apex the whole boundary sits inside the $30°$ wedge.

I added a caveat the brief did not have. The natural over-generalisation — "a polygon vertex with
interior angle $< 60°$ is exceptional" — is **false** for reflex polygons, where the curve leaves the
wedge even though the local angle is small. The hypothesis is containment of the *whole* curve, and I
said so, because that is exactly the kind of slippage this file is supposed to catch.

**Rotation trick.** Sound, and it does double duty. $q \in J \cap \rho_{60°}(J)$, $q \ne O$ gives
$|Oq| = |O\rho^{-1}(q)|$ with a $60°$ apex, hence equilateral. I used it in §2 as well, because the
fixed point $O$ is *always* in $J \cap \rho(J)$ and is precisely the degenerate solution — the
cleanest concrete instance of the degeneracy rule I could find, so the two sections reinforce rather
than repeat each other.

I also worked out and wrote down *why* it has no square analogue, rather than just asserting it:
isosceles-with-a-$60°$-apex closes a triangle from three points, whereas a square needs a fourth
vertex which the construction determines but does not place on $J$. That is the concrete standard
against which "why doesn't this transfer?" answers should be judged, and asserting the
non-transfer without the reason would have been exactly the kind of unchecked line I am ruling out.

## Mathlib / Jordan curve theorem — my own check

No `lean/.lake`, so no local checkout. The repo pins `leanprover/lean4:v4.33.0` and mathlib
`inputRev: v4.33.0` (`lean/lean-toolchain`, `lean/lake-manifest.json`), so I read the Mathlib
sources at that exact tag from `raw.githubusercontent.com`:

1. `Mathlib.lean` (8317 module imports). Grep for `Jordan` returns only `Algebra.Jordan.Basic`,
   `JordanChevalley` (×2), `GroupTheory.GroupAction.Jordan`, `Order.JordanHolder`, and the measure
   decompositions — i.e. **Jordan algebras and Jordan decomposition, no Jordan curve theorem**.
   `Winding`, `Alexander`, `InvarianceOfDomain`, `Brouwer`, `Excision` return **nothing**.
2. `docs/1000.yaml` at the same tag — Mathlib's own theorem index, where formalised entries carry a
   `decl`/`decls` field and externally formalised ones carry `authors`/`url`. `Q260928: Jordan curve
   theorem` has a title and **nothing else**. Brouwer's fixed-point theorem carries only a Lean 3
   external project link. So: not in Mathlib, and no Lean formalisation known to that index.
3. Singular homology does now exist at this tag —
   `AlgebraicTopology.SingularHomology.{Basic, HomologyZero, HomotopyInvariance,
   HomotopyInvarianceTopCat}` — but there is no excision and no Mayer–Vietoris, so the standard
   route to JCT is not there either. This is the one place the picture is moving, which is why the
   rules tell agents to re-run the check rather than quote my paragraph.

I did run a WebSearch, which agreed, but its answer is a model-written summary of snippets and I did
not rely on it; the two source-level checks above are what the rules file cites. (Prior repo
notebooks record summaries being mistaken for sources — PR #36, PR #21.)

**Consequence I wrote into §6.3.** JCT-dependent steps are a genuine large Mathlib gap under

in the same file. Those are real Lean targets and I listed them in §7.

## What I dropped or changed from the brief

- **Nothing dropped outright.** All five points survived; I judged each one to be carrying weight.
- **Merged the numerics point into its own short §5 rather than a general "numerical practice"
  section.** The brief's exactness point and the polygon-control filter are about the same artifact,
  so §3.3 states the filter and §5 states the arithmetic discipline; splitting reproducibility
  boilerplate out again would have duplicated `../../RULES.md` §4 for no gain.
- **Added §4 (approximation arguments), which the brief did not ask for.** "Prove it for polygons,
  then take limits" is the attack that will actually be proposed, and it is the exact shape that
  fails for squares. Folding it into the degeneracy rule would have hidden it. Its four
  requirements (topology on curves; the limit need not be Jordan; uniform $\delta$; the square
  non-transfer) are the ones I would want a reviewer to check first.
- **Added the "not found ≠ open" rule to §6.1**, and the rule that recalled author names may live in
  an attack README flagged unverified but never in the known-results table. Given the brief's
  framing that the triangle case may already be a theorem, the realistic failure here is an agent
  finding no paper and concluding the problem is open — a much likelier error than a bad citation.
- **Added the reflex-polygon caveat to the wedge test** (above), so the filter is not itself
  over-applied.
- **Deliberately did not name a candidate reference** for the triangle case. I have recall of a
  plausible one, but I have not read it, and writing it into a rules file would be exactly the
  laundering the file forbids two sections later. It belongs to the README worker with a source in
  hand.
- Cut one full pass for length after the first draft (255 → 229 lines) — the brief was explicit that
  a rules file nobody reads is worse than none, and the sibling files are 111 and 149 lines.
