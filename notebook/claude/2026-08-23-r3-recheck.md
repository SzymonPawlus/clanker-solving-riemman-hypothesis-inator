## Arithmetic

Q(sqrt(3)) as pairs of `fractions.Fraction` (a, b) meaning a + b*sqrt(3). Exact `sign()`:
zero iff a = b = 0 (irrationality of sqrt(3)); same-sign cases immediate; mixed signs by
comparing a^2 with 3b^2. **No float in any accept/reject decision.** `selftest.py` checks the
sign routine against mpmath at 1000 dps on 20000 random inputs — 0 mismatches — plus ring
identities and 21 parser shapes (11 accept, 10 reject, including the decimal string
`"12.928203230275514"` that `RULES.md` §2 bans).

## Controls (the part that makes the pass mean something)

- Positive: triangular lattices n = 3, 6, 10, 15, 21 (`cited`, Oler 1961) — all accepted, all
  reported tight.
- Negative on n = 17: broken separation → reject; point past edge BC → reject; point below edge
  AB → reject; deflated s → reject; **inflated s → accept but NOT tight** (the important one:
  an inflated s must not be rejected, it must be reported as loose); decimal string → parser
  rejects.
- External consistency, exact: claimed s must lie between the bracketing `cited` triangular
  values. Passes. This is the control that would have caught the author's self-named worst-case
  exposure — d written into the `side_length` field — since each certificate's d falls below its
  lower bracket.
- Float diagnostic, explicitly non-load-bearing: minimising the equilateral support function over
  rotations finds no orientation in which any of the three point sets fits a smaller triangle. So
  the tightness is not an artefact of the fixed placement.

## What I am least sure of

Nothing in the arithmetic — that is exact, self-tested and controlled. The soft spot is
**scope**: this confirms three upper bounds and nothing else. n = 17, 24, 31 are open; a tight
certificate is tight for its own point set only. I also did not verify the published
Graham–Lubachevsky record values themselves (literature work, verification-critical, not mine
today) — only that the claimed s values are arithmetically consistent with the quoted m via
s = 2/m + 2*sqrt(3) to 4e-14, and that they sit inside the bracket forced by the cited triangular
values.

Second-order worry: my checker and the author's could still share an error inherited from the
*specification* rather than from the code — if problem `RULES.md` §2's convention itself were
misstated, two faithful implementations would agree and both be wrong. That is exactly what the
cross-family check exists for and is another reason this same-family agreement must not be
treated as a promotion.
